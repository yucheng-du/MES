# MES API

[简体中文](README.zh-CN.md) · English · [Project README](../../README.md)

A modular monolith built with Fastify 5, TypeScript, and PostgreSQL 17. It requires Node.js 22.12 or later. See the [API contract](../../docs/API-CONTRACT.md) for public endpoints and payloads.

## Local development

Run these commands from the **repository root**. Root scripts load the root `.env`; directly invoking a workspace server script does not do that automatically.

```bash
npm ci
npm run db:local
npm run db:migrate
npm run db:seed
npm start
```

The local database helper requires PostgreSQL command-line tools on `PATH`. It creates development and test databases and writes `.env` only if it does not exist. Alternatively, copy the root `.env.example` to `.env`, configure separate `DATABASE_URL` and `TEST_DATABASE_URL` connections, and run the migration and seed commands. Seeding creates public development demo data, is refused in production, and skips databases that already contain users.

`npm start` runs only the API. `npm run dev` starts both the API and web application. The example environment uses API port 4300; without `HOST` or `PORT`, the server defaults to `127.0.0.1:3000`.

For production, apply migrations and create a private administrator using the [deployment guide](../../docs/DEPLOYMENT.md). Bootstrap accepts optional `ADMIN_USERNAME` and `ADMIN_NAME`; `ADMIN_PASSWORD` must be explicitly supplied and contain at least 12 characters. It refuses initialization when an administrator already exists. `NODE_ENV=production` requires HTTPS `APP_ORIGIN` and secure cookies. Containers need `HOST=0.0.0.0`; enable `TRUST_PROXY=true` only behind a trusted reverse proxy. Do not expose a seeded development database as production.

## Verification

From the repository root, with `TEST_DATABASE_URL` configured in `.env`:

```bash
npm run typecheck
npm test
npm run test:integrations
```

Database tests refuse connection names that do not end in `_test`. They rebuild the dedicated database's `public` schema; do not share that database with another test process or business environment. Tests use real PostgreSQL, including concurrent connections, injected pay failures, and transaction rollback. See [testing](../../docs/TESTING.md) for setup and verification boundaries.

## Business and security constraints

- State-changing requests validate their origin. Sessions use random 256-bit tokens, store only token hashes in the database, and expire after 12 hours. Passwords use scrypt and login is rate-limited. Disabling users, changing roles, or resetting passwords revokes sessions.
- The server validates roles and record ownership. Operators act on their own reports and read their own pay. Pay rewards and deductions are generated by approval use cases.
- Work orders snapshot the process route and rates. Operations advance in order, and partial completion stays on the current operation. Workers or managers can resubmit rejected reports without changing production quantities.
- Finished goods balances are keyed by sales order and product; make-to-stock uses a separate null-order balance. Concurrent changes lock the balance row. Cross-order issues, negative stock, and receipts above completed output are rejected.
- Production, inventory, and other designated actions carry `requestId`. An identical retry returns the original result; reusing a key with different content is rejected. Approval, pay, and audit commit in one transaction.
- Scrap requires a quality inspector or manager's approval. Scrap cannot directly reduce completed output already received into stock. Reviewers may explicitly set deduction/reward unit prices; both default to zero. If all units are scrapped, completion with zero good units is allowed.
- Shared definitions validate management record fields, reference existence, revisions, and transitions. Material and consumable receipt/issue approvals update real inventory. Hourly-work and safety reward/penalty approvals create pay entries with unique sources; approved hourly work cannot exceed 24 hours per worker per day.
- Work tasks and Andon records require formal feedback after submission, from the assignee or a manager, before approval. Draft results or a previous round's feedback cannot bypass handling. Feedback records its author, time, revision, and audit event.
- SSE sends invalidation notices only to signed-in users, not business details. Data refetches enforce permissions again. The stream checks session validity every 15 seconds. MQTT is registered through the separate integration module.
- Multipart uploads use `POST /api/files`; administrators, managers, and quality inspectors may upload. Signed-in users fetch metadata and download files through authenticated endpoints. Work documents may reference up to 10 existing attachments. `FILE_STORAGE_DIR` stores content; the database stores metadata and checksums. Back up both.

## Automatic report approval

Defaults are enabled, a five-minute delay, CNY 2,000 per report, partial completion allowed, and standard-time checks off. Administrators/managers configure the current revision through `GET/PATCH /api/settings/auto-review`: delay is 0–1440 minutes, the amount limit is positive with at most two decimal places and a maximum of 1,000,000,000, the duration ratio is 0–1, and quantity matching is optional. `POST /api/settings/auto-review/run` checks once while respecting the switch and delay.

The API checks at startup and every 60 seconds. `createApp()` does not enable this worker by default in tests; the server entry point explicitly enables it. A database session lock selects one executor across instances. Each review locks settings → work order → report → worker and shares the manual approval transaction. Unique pay sources prevent duplicate pay. Disabling waits for in-progress reviews; server shutdown waits for started review transactions.

Only reports completed after the current activation boundary are eligible. Earlier backlog, rejected/resubmitted reports, closed orders, disabled workers, invalid quantities/times, pending or approved scrap on the same order, and threshold failures require manual review. Referral persists when rules are relaxed. Migration reconstructs historical rejection flags from audit records. Chinese-source reasons are translated by the web catalog for English display.

Runs record source, rule revision, batch, and per-report result. Confirmed pay-source or business-constraint conflicts roll back and go to manual review. Temporary database connection, timeout, or deadlock failures remain eligible for a later retry. The settings panel and dashboard expose queue totals and run results. `GET /api/reports?reviewMode=manual|automatic|pending_auto` selects the corresponding queue. See [automatic approval](../../docs/AUTO-REVIEW.md) for operational behavior and scope.

## Source map

- `src/production.ts`: production and finished goods inventory.
- `src/report-review.ts`: shared approval and pay transaction.
- `src/auto-review.ts`: configuration, rule evaluation, and background execution.
- `src/catalog.ts`: management records and approval effects.
- `src/auth.ts`: authentication and authorization.
- `src/db.ts`: transactions and idempotency.
- `src/integrations.ts`, `src/files.ts`: equipment ingestion and authenticated attachments.

SQL values are parameterized; dynamic table and ordering choices come from static allowlists in code. Container deployment, live equipment, and physical printing need acceptance in the target environment; local tests do not establish those outcomes.
